# Re-provisioned nodes (HPCM)

The cluster manager (HPE HPCM) re-provisions nodes from time to time: the node
comes back with a fresh OS and an empty local disk. It never changes files on a
running node. This page is how the deployment survives that, for compute nodes
and for the admin node (RKE2 server).

The rule: **whatever a node holds is either regenerated by `site.yml` from the
deployer, or lives on storage that outlives the node.** After any
re-provision, run `site.yml` again; nothing else is needed.

```sh
ansible-playbook -i inventories/<site>/hosts.yml site.yml
```

Run the whole playbook, not `--limit <node>`: other nodes' facts are needed
(e.g. for `/etc/hosts`), and every play is idempotent, so the untouched nodes
report no changes.

## Where state lives

| State | Survives because |
|-------|------------------|
| CA, certificates, tokens, passwords, uid/gid map | in `inventories/<site>/secrets/` on the deployer (the HPCM admin node). Back it up. |
| RKE2 node password of each node | derived from `secrets/rke2-node-password-seed` and the node name, so it is the same after a re-provision |
| RPMs, images, binaries, registry contents | rebuilt from the bundle (`hpc_data_root` on the admin node) |
| etcd (every Kubernetes object, Rancher, RKE2's own CAs) | hourly snapshots in `hpc_backup_dir`, restored automatically |
| accounting history (`/var/lib/hpc/acct/acct.db`) | hourly copies in `hpc_backup_dir`, restored automatically |
| NFS StorageClass volumes, homes (when enabled) | NFS exports under `hpc_persist_root` |
| Keycloak database | `hpc_keycloak_db_dir` under `hpc_persist_root` |

`hpc_persist_root` is a directory on storage that is still there after the
admin node is wiped, e.g. on the CephFS mount the nodes get at boot:

```yaml
# inventories/<site>/group_vars/all.yml
hpc_persist_root: /rhev/data-center/mnt/cephfs/rke2
```

With it set, the defaults become:

| Variable | Default with `hpc_persist_root` | without |
|----------|--------------------------------|---------|
| `hpc_backup_dir` | `<root>/backup` | `''` (no backups) |
| `hpc_nfs_home_export` | `<root>/home` | `/c/home` |
| `hpc_nfs_k8s_export` | `<root>/k8s` | `/c/k8s` |
| `hpc_keycloak_db_dir` | `<root>/keycloak-db` | `/var/lib/hpc/keycloak-db` |
| `hpc_nfs_export_fsid` | `true` | `false` |

Each can still be set on its own. Preflight fails if `hpc_persist_root` is on
the root filesystem (the mount is missing); `hpc_persist_require_mount: false`
turns that check off.

## A compute node was re-provisioned

`site.yml` reinstalls RKE2 and writes the same node password as before, so the
server accepts the node under its old name. Its Node object, labels and
taints are kept. Images are pulled again from the admin node's registry.

Without the fixed password, RKE2 would generate a new random one, and the
server would refuse the node ("Node password rejected, duplicate hostname").

## The admin node was re-provisioned

With `hpc_backup_dir` set, `site.yml` sees an RKE2 server with no etcd data
and a snapshot in `<backup dir>/etcd/`. It then:

1. rebuilds the node as usual (repo, registries from the bundle, NFS exports
   on the persistent storage, RKE2 config);
2. copies the newest snapshot to local disk and runs
   `rke2 server --cluster-reset --cluster-reset-restore-path=<snapshot>`;
3. starts RKE2. The restored server has the same CAs, service account keys and
   objects as before (snapshots carry RKE2's bootstrap data, encrypted with
   the server token from `secrets/`), so the agents reconnect by themselves
   and existing kubeconfigs keep working;
4. refreshes the compute nodes: restarts `rke2-agent` and kube-proxy there,
   and recreates every pod of the platform namespaces that runs off the admin
   node (canal, CephFS node plugin, CoreDNS replicas). The restored data is
   older than what their watchers last saw, and they miss changes until the
   store catches up: in the lab, pods lost network policy (Calico) and new
   Services did not resolve (CoreDNS) until these restarted. Project pods keep
   running; a project's own controllers that watch the API catch up by
   themselves once the cluster has made as many changes as the snapshot was
   behind (restart them if they look stuck);
5. restores the newest accounting database before the recorder starts;
6. re-applies the platform (helm upgrades, tenants), which finds everything in
   place.

Anything changed after the newest snapshot is lost: at most one
`hpc_backup_schedule` interval (hourly by default). Pods on compute nodes keep
running throughout; they lose only the API while the admin node is down.

`hpc_rke2_restore: false` turns the automatic restore off (the server then
starts with an empty cluster).

### Restoring by hand

To go back to an older snapshot, or after a failed automatic restore:

```sh
systemctl stop rke2-server
cp <backup dir>/etcd/hpc-backup-<node>-<time> /var/lib/rancher/rke2/server/db/snapshots/
rke2 server --cluster-reset --cluster-reset-restore-path=/var/lib/rancher/rke2/server/db/snapshots/hpc-backup-<node>-<time>
systemctl start rke2-server
# then, on every compute node: systemctl restart rke2-agent, and stop the
# kube-proxy container (crictl stop; kubelet starts it again)
# and recreate the platform pods that run on compute nodes, per platform namespace:
kubectl -n kube-system delete pod --field-selector spec.nodeName!=<admin node>
```

## Backups

`hpc-backup.timer` on the admin node (`hpc_backup_schedule`, hourly) and the
end of every `site.yml` run write:

```
<backup dir>/.hpc-backup                    marker; hpc-backup refuses to run without it
<backup dir>/etcd/hpc-backup-<node>-<time>  on-demand etcd snapshot
<backup dir>/acct/acct-<time>.db            consistent copy of the accounting database
```

The newest `hpc_backup_keep` (48) of each are kept. Status:
`systemctl list-timers hpc-backup.timer`, `journalctl -u hpc-backup`.
`verify.yml` checks that both backups are less than 150 minutes old.

**The etcd snapshots contain every secret in the cluster.** The backup
directory is root-only (0700). On a CephFS mount that every node has, root on
any node can still read it: prefer a CephFS path or client key that only the
admin node can use.

## CephFS as the persistent storage

- **etcd stays on local disk.** Only snapshots go to CephFS. etcd needs low
  fsync latency, which a network filesystem does not give it.
- **NFS exports on CephFS** need a fixed `fsid` per export (CephFS has no
  device number nfsd can use); `hpc_nfs_export_fsid` adds `fsid=7101` (homes)
  and `fsid=7102` (StorageClass). An NFS-Ganesha gateway on the Ceph side is the
  alternative ([ceph.md](ceph.md)).
- **The Keycloak database on CephFS** works (low write volume). Its directory
  is labelled `container_file_t` for SELinux; if the CephFS mount does not keep
  SELinux labels, mount it with
  `context="system_u:object_r:container_file_t:s0"`.
- Ceph becomes a dependency of the admin node's services: if the mount is
  missing at boot, the NFS exports and Keycloak do not start, and backups fail
  loudly. RKE2 itself starts from local disk.

## Testing in the lab

The lab's admin VM has a second disk mounted at `/rhev/data-center/mnt/cephfs`
that stands in for the CephFS mount. `lab.sh reprovision <node>` wipes a node's
root disk and boots it with a new cloud-init instance, like HPCM does. The
persistent disk is kept.

```sh
../lab/lab.sh reprovision c2 && ansible-playbook -i inventories/lab/hosts.yml site.yml
../lab/lab.sh reprovision a1 && ansible-playbook -i inventories/lab/hosts.yml site.yml
ansible-playbook -i inventories/lab/hosts.yml verify.yml
```
